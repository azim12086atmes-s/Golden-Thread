# Golden Thread gameplay parity audit

**Pinned source:** `azim12086atmes-s/Golden-Thread`, commit `a6c20a4f9ceabec4fbd544ca7c73658b005c2318` (the requested `claudes-current-work/3d-builds` snapshot).  
**Compared runtime:** the local `golden-thread/party/` multiplayer adaptation and `golden-thread/server/party.mjs`.  
**Method:** static read of the pinned `src/Game.ts`, `src/core/state.ts`, `src/ui/UI.ts` and referenced modules, plus the local party adaptation. No checkout/build/browser session or gameplay tests were run. “Active” below means there is a runtime construction/update or interaction/UI path in source; it does not mean independently verified playable or bug-free. The pinned repository returns 404 for `party/main.js`, `party/life.js`, and `server/party.mjs`; that party implementation is a separate local extension, not present in this pinned snapshot.

## Finding

The pinned source is a much broader single-player game than the source from which the local party layer was made. Its expanded systems are not wired into local PartyLife. The party adaptation retains a substantial earlier slice of Golden Thread (core gathering, crafting, quests, townsfolk, relationships, personal plots, animals, lanterns, rides, caravan, van, and guide), then adds its own shared party / story / minigame / festival server. It does **not** currently preserve the newer economic, civic, housing-interior, service, travel, diary, or profile systems from the pinned Game.

The newer systems are more than orphaned modules in the pinned source: `Game.ts` constructs many of their views/systems; its frame advances their simulation; `findTarget()` detects their world locations; `interact()` routes them to UI actions; and `UI.ts` has corresponding panels. A subsystem’s presence in that chain establishes an active source path, but not a claim that every subfeature, edge case, or visual path has passed runtime QA.

## Wiring evidence in the pinned source

- `src/Game.ts`: constructor builds the newer systems/views (including `Dragons`, `InstitutesView`, `FieldsView`, `HarboursView`, `HouseInterior`); frame updates weather, season, ambience, traffic, civic and festival visuals; a repeating lifecycle tick invokes `tickCharity`, `tickInstitutes`, `tickFields`, `tickSupply`, `tickBusinesses`, `tickInventions`, `tickHomes`, `tickLearning`, `tickWeavers` and `tickParents`. `findTarget()` covers institutes, commercial fields, people in need, harbors, bus/tram stops, Sky Isles stations, doors, and caves; `interact()` routes those targets to their panels or mechanics.
- `src/ui/UI.ts`: panel type includes work, harbor, bus, tram, air, field, institute, care, diary, account, homes, houses, property and market, among others. The file contains specific panel methods such as `openField`, `openCare`, `openTramStop`, `openBusStop`, `openHarbour`, `openInstitute`; it contains institute research and business controls, and uses DiaryPanel/AccountPanel.
- `src/core/state.ts`: the persistent model has dedicated records for sponsored people, home floors, penthouses, institutes, learners, hires, pantries, fields, routes, shipments, glut, work, thesis/degrees, products, businesses, installed inventions, homes/stores, errands, parents, certificates, homecomings, diary, and time played. Separately, `src/core/profiles.ts` supplies profile-based save identity. This indicates designed persistence contracts, not that every save migration or interaction was tested in this audit.
- Relevant module files: `src/economy/{business,supply,fields,services,manufacture,inventions,crews,storage}.ts`; `src/institutions/{institutions,catalogue,research,opportunities,certificates}.ts`; `src/charity/{charity,upskill}.ts`; `src/travel/{ferry,bus,streetTram,air,gondola}.ts`; `src/housing/{HouseInterior,parents,penthouses,designs}.ts`; `src/world/{caves,harbours,Weather}.ts`; `src/diary/diary.ts`; `src/core/profiles.ts`.

## Concrete integration gap and implications

The party code is a second runtime composition rather than an adapter around the pinned `Game`. `party/life.js` creates its own `newGame()`, QuestSystem, Messages, Housing, HousingView, NPCs, Townsfolk, Animals, TownDressing, WonderSites, Guide and PartyCaravan, then advances only those. Its `nearest()` recognizes NPCs, gather nodes, animals, plot signs, owned farm beds and lanterns. Its tabs are journal, bag, craft, trade, friends, home, rides, van and company. Its constructor/update contains no fields, supply, businesses, institutes, charity, jobs, expanded travel, house interiors, diary, or profile/account modules. The local party does preserve the original gated unicorn and dragon ride catalog, but the pinned wild-dragon ecosystem and new public transport systems are not wired into its scene/loop. The server shares positions and selected party activities; the additional game state remains local per player and is not a shared town economy.

Thus, calling the party game “the complete current Golden Thread gameplay” would be inaccurate. It preserves and extends the earlier subset. To achieve parity, additions need to be deliberately composed into the party runtime: per-player persisted state and UI actions, spatial target detection, visibility/privacy policy, environment updates, and the pinned economy’s game-time ticks. Avoid duplicating the pinned rule systems: adapt them around `GameState` and preserve their costs, prerequisites, days, capacity and delivery behavior. The current party loop advances its own local clock, while the pinned systems’ economy and schedules are expressed in `st.minutes`; that clock ownership is an integration contract that must be resolved rather than silently running one player’s economic schedule for everyone.

## Limits

This is a source-level wiring/parity audit against the requested SHA, not a feature acceptance test. It does not establish that all newly imported panels are reachable in all regions, that every subsystem is balanced, or that the pinned source builds. It also does not treat folder presence, state fields, or UI imports alone as proof of playable behavior; the “active” classifications above rely on the Game update/interaction paths and corresponding UI methods described above.

## Privacy review: narrative and family data

The pinned single-player game is authored around a named pair, their relationship, and a family caravan. This is important for migration: filtering server player IDs alone would not filter locally generated narration or NPC models. A shared party client that simply mounted the pinned Game could show the same authored family on every guest's own screen, and its opening can stage the pair together even when no remote companion object is present.

The current local multiplayer code has stronger separation for **invited** private companions than the pinned standalone Game’s story model: server presence is projected by role, and PartyLife does not load the pinned StoryScene, ThreadScene, CakeScene, parents, account panel, or title screen. However, PartyLife’s generic guide and its default local caravan remain semantically pair/family content on public guest clients. The distinction matters: the sibling/pet models do not disclose the hidden companion’s network identity, but can still suggest that the guest is playing a coupled/family narrative.

For a migration that keeps Golden Thread systems intact, the narrow policy should be to gate or rephrase the presentation layer by role, not remove the underlying rules or alter progression: run intimate pair cutscenes only in a private birthday/companion view; avoid creating/rendering an uninvited second protagonist for guests/observer; suppress pair-specific names/letters/parent toast strings from public messages; and keep local caravan characters explicitly local or filter them for guest/observer roles if the user wants no relationship cue at all. The shared rule systems (quests, skills, institute, charity, fields, rides) can remain available in each player’s private state.
