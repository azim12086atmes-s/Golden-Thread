The commit/tree comparison clarifies how these relate. `3d-builds/claudes-current-work` contains every path in `latest-working-on-going`, but only 54 of those 126 blobs are byte-identical; 72 paths changed and 224 files were added. The 3D branches share 212 identical files; `codex/3d-model-renders` differs from `codex/3d-models` at one shared blob and adds 24 paths, namely the 19 PNGs, two workflows, preview page, and two render scripts. Both 3D branches share 213 paths with current-work, of which 101 blobs match and 112 differ; current-work adds 137 paths relative to `codex/3d-models`. Thus the render branch’s images are useful visual references, but its code should not be treated as the current-work code snapshot.

`birthday/14-player-celebration` contains all 126 paths from `latest-working-on-going`; 114 are byte-identical and 12 changed, with 73 party/hosting additions. Its relevant wrappers are split: `party/main.js` constructs the party scene, while `party/life.js` creates original Npcs, Townsfolk, Animals and TownDressing, attaches `World.onRegionLoaded`/`onRegionUnloaded`, processes already-loaded regions and updates those systems. The earlier audit incorrectly inferred missing lifecycle hookups by reading only `PartyGame`; those systems are active. The party wrapper does not, however, set up every newer current-work system such as Weather, Traffic, FestivalAir, CityScreens, CivicMarkers and Dragons.

The only shared filename between `gh-pages` and each source tree is root `index.html`; all are generated/different blobs. The published branch is a deploy history, not an alternative source branch. Across the listed trees, procedural Three.js geometry is the runtime model strategy: the checked-in images are before/after or monument renders, not runtime mesh inputs. No asset count by itself captures the large difference between current-work’s gameplay/world systems and the focused model branches.

Visual-specific takeaways: use `codex/3d-model-renders/art/monument-renders/*.png` for the 19 regional monument reference renders and `monument-preview.html` as their review harness; use `docs/renders/night-dragon-before-after.jpg` as the separate current-work dragon before/after artifact. The current-work commit `a6c20a4` itself is a small performance refinement (skip monuments beyond fog and far meadow grass under quality pressure), not the source of the renders. The 3D-model-renders head commit restores original monument models in `src/world/architecture.ts`; the 3D-models head removes the temporary validation workflow. `gh-pages` head publishes current-work `a6c20a4` and keeps prior bundled versions.

### Monument PNG provenance

The 19 committed files in `art/monument-renders/` are **headless-browser WebGL screenshots of an isolated preview scene**, rendered with SwiftShader software GL—not screenshots of the running Golden Thread game and not Blender/offline raster output. `.github/workflows/render-3d.yml` starts Vite, installs Playwright and Chromium, then runs `scripts/probe/render-standalone.cjs`; that launches Chromium with `--use-angle=swiftshader`, loads `monument-preview.html?land=<id>`, and calls `page.screenshot`. The preview imports `GeoBuilder` and `buildLandmark` directly, places just the generated landmark on a 1500m plane, adds its own hemisphere and directional lights, positions a 43° camera from its bounds, and renders one still frame. It does not instantiate `Game`, `World`, the real sky/fog/bloom/postprocessing, traveller framing, meadow, weather, or traffic. These are useful geometry inspection renders, but must not be represented as actual in-game screenshots. `scripts/probe/monument-renders.js` is a separate script that drives `window.dev`/`game.trav` and `shot()` through the game probe prelude; the workflow does **not** call it. `docs/renders/night-dragon-before-after.jpg` provenance is not established by those render scripts, so I have not classified it as an in-game capture.

## Spatial conventions and party-scene adapters

- World axes are Three.js standard: **x/z are horizontal world metres, y is up**. Current `regions.ts` defines 700m square regions, `CITY_RADIUS=240`, and 5×4 grid coordinates centred on home `(col=2,row=1)`; `regionCenter` is `((col-2)*700,(row-1)*700)`. `RegionBuilder.buildRegion` authors town geometry and placements in metres local to the region centre; `H(lx,lz)` explicitly samples `terrainHeight(c.x+lx,c.z+lz)`, and the built group is translated to `(c.x,0,c.z)`. The landmark group uses the same centre-offset convention (`World.buildLandmark`).
- `GeoBuilder` frame matrices bake local transforms into geometry. Its `box`, `cyl`, and `cone` helpers translate primitives by half their height, so their supplied y is a **base elevation**; `sphere` remains centre-positioned. The castle `Kit` has the same base-oriented `box`/`cyl` helpers and `body`/wall helpers that shift from base y. When adapting raw Three.js primitives, make this origin convention explicit or grounded parts will float/sink by half-height.
- Character dimensions are metres before hero scaling: hip .82, waist .95, shoulder 1.36, neck 1.4, head radius .155, head gap .16. The detached head's top is about 1.87m unscaled. `HERO_SCALE.boy=1.08` gives about 2.02m; girl's computed scale is about .842, giving about 1.57m, while her forehead is deliberately 2cm below his shoulder. The unscaled butterfly wing height is 13.35m (`1.78*7.5`), so check actual paired character/framing with `CharacterModel.scale`, wing plane and `Travellers` clearance rather than framing a 1.8m person as if wings were proportionate.
- Current `MeadowField` uses `terrainHeight` and `groundColor` for each deterministic cell; `grassy/openGround` exclude non-green terrain, roads, paving, plots and plazas; flowers/grass use each `regionAt` locale. It streams instanced near/mid/far rings and binds the shared wind, lamp, sun and night uniforms. `Game.frame` updates wind, water/night uniforms and nearby lamps. The birthday branch's `party/living-grass.js` is a separate modelled-blade field with its own local sway shader and fixed sample colors; `party/landscape.js::grassAt` checks the custom palace mesh, real source terrain, town/plot exclusions, bridges and altitude. It is a useful bounded adapter, but it is not visually identical to the current Meadow (textured crossed tufts, locale-tinted flowers, matching lighting/wind). The older birthday `World` does not contain the newly added current-work `MeadowField`; if current World/Meadow is transplanted, check for duplicated party grass and connect `updateWind`, lamp/night and quality controls.
- The party palace is deliberately transformed into shared Golden Thread world coordinates: source layout coordinates are multiplied by `PALACE_TRANSFORM.scale=.45`, then offset `(0,77.3,-2700)`. Palace layout `S=2.75` is already baked into many source coordinates; `sourceScale:2.75` in shared config is unused by the current adapters and must not be multiplied again. `PartyScenery` keeps castle geometry in its transformed group, while player/objective/cake coordinates, `decor`, and `PalaceLandscape` are already world-space. Its `toSource`/`toWorld` adapters invert/apply the transform for palace ground and collision. Collider radii are converted using `/SCALE`; elevations return as `sourceHeight*SCALE+OFFSET.y`. `PalaceLandscape::heightAt` samples its own triangles, then the scenery falls back to original `surfaceAt`; its `grassAt` refuses paved/plaza/bridges and rejects mismatched elevation. Reuse these boundaries rather than moving the whole Golden Thread world or applying the transform to world-space props twice.
